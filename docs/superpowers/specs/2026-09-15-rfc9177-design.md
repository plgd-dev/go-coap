# RFC 9177 implementation design

Status: milestone 1 wire and storage foundations implemented; transfer engines, connection integration, capability discovery, and interoperability remain planned.

## Purpose and baseline

Implement opt-in Q-Block transfers for unicast UDP and DTLS while keeping application handlers and `Do` body-oriented. The planning baseline is `v3.5.4-3-gdefc9c6`, Go 1.25.0. The user's supplied Q-Block summary is the starting specification; this document records the implementation boundaries and refinements from source review.

## Scope

- NON Q-Block1 POST/PUT and Q-Block2 GET, client and server.
- Include Q-Block2 response bodies to POST/PUT, including combined upload/download exchanges.
- CON capability discovery must work before NON payload transmission is enabled.
- Both Q options ship together. Intermediate milestones are internal foundations, not advertised RFC 9177 support.
- Defer Observe, multicast, TCP/TLS Q transfers, BERT, OSCORE processing, FETCH/PATCH/iPATCH application support, and generic `WriteMessage` integration.
- Keep `WithBlockwise` behavior unchanged.
- No new production dependency in the foundation milestone.
- Do not refactor classic `BlockWise` into a shared transfer engine.

## Components and ownership

`net/qblock` owns protocol state, sparse bodies, bounded retained response bodies, recovery, and transfer timers. An adapter in `udp/client` supplies packet I/O, token/MID allocation, application dispatch, and lifecycle integration. DTLS uses the same connection implementation.

The core must be testable without sockets or wall-clock sleeps. Give the eventual engine explicit packet, deadline, cancellation, and send-result events; emit send/deliver/release actions. Fix the engine's exported interface in milestone 2, after the foundation types are available. Do not create an unused generic event framework during milestone 1.

The connection adapter checks owned response tokens before classic routing. Q request fragments are identified by options and body identity. Terminal responses may have no Q option. Keep MID ownership for NON messages so Reset messages can cancel the correct transfer. Allocate tokens through one collision-checked connection namespace shared with ordinary requests and Observe.

Handlers receive one complete request. Copy the resulting response into engine-owned storage before `ResponseWriter` releases its pooled message. The engine fragments that response and serves repairs without reinvoking the application. Retain completed-request identity and its outcome for a bounded period to prevent a late duplicate upload from running the handler again. This is bounded duplicate suppression, not a promise of exactly-once application execution across process restarts.

No incoming pooled message is retained past its callback by the Q engine. Retained tokens, options, payloads, and control metadata are copied. Every completion, cancellation, expiry, send failure, and connection shutdown releases owned state.

## Wire boundary

Add `QBlock1=19`, `QBlock2=31`, `RequestTag=292`, and `AppMissingBlocksCBORSeq=272` with names, formats, and length definitions. Preserve repeated options in the existing `message.Options` representation.

Use an additive UDP decoder entry point accepting an option-definition map. The connection's Q-aware decoder uses a private copy of definitions that preserves raw QBlock1/QBlock2/RequestTag values, including invalid lengths. Validate their lengths and multiplicity before dispatch. Do not mutate `message.CoapOptionDefs` or change the permissive default decoder globally. Missing or malformed required metadata must prevent fragment acceptance.

Disabled Q requests are rejected before reaching application handlers. For NON, select silence as the disabled-mode policy; CON gets Bad Option. Mixed classic/Q options are rejected. Response validation must not generate request-style error responses to response messages. Structurally undecodable datagrams remain decoder errors.

## Body storage

Use a map of copied blocks and a received-block count rather than allocating the peer's announced body size on the first fragment. Validate size, offset, fragment length, and final-block consistency before allocating. Assemble a contiguous owned body only after completeness is established.

Q-Block1 identity comprises the connection/security context, request operation options, and the full Request-Tag collection. Q-Block2 assembly comprises the initiating operation and representation ETag. Different identities never share a body. A changed representation must not append to an earlier partial body.

Body metadata records exact announced size, selected SZX, optional Content-Format with presence tracked separately, and representation identity. Do not require Content-Format where the protocol permits omission. Received fragments preserve the body's metadata. Decide SZX before sending payloads; handle peer size negotiation explicitly in milestone 2 rather than changing offsets in an existing assembler.

The first storage primitive takes an explicit byte limit. Later engine configuration also limits aggregate retained bytes, active transfers, tokens, and deadlines. Count the final assembly allocation against the aggregate budget; a per-body cap alone does not bound connection memory.

## Timing and recovery

Use the user's specified defaults: MaxPayloads 10, NonTimeout 2 seconds, NonReceiveTimeout 4 seconds, NonMaxRetransmit 4. Additional normative details are anchored in [RFC 9177 §7.2](https://www.rfc-editor.org/rfc/rfc9177.html#section-7.2): fixed payload-set boundaries, one randomized inter-set delay per body, receive-timeout constraints, matched Continue signals, repair pacing, and probing-rate accounting.

Use one deadline scheduler per connection, with injectable time and jitter; do not shorten the global four-second periodic runner for every connection. No network I/O, handler invocation, or timer callback runs under a transfer-state lock. Schedule only the next deadline and cancel the scheduler on connection closure.

CBOR recovery handling follows [RFC 9177 §5](https://www.rfc-editor.org/rfc/rfc9177.html#section-5). Use unsigned integer sequences without an array wrapper. The proposed receiver policy collapses equal adjacent numbers and ignores descending or malformed reports without making a valid transfer fail. Validate reported indices against this body's block count and cap report length before allocating.

## Capability and fallback

Proposed application surface: `options.WithQBlock(options.QBlockConfig{...})`, with `PreferKnown` and `Require` modes. Put the canonical configuration type in `net/qblock` and use aliases in `options` to avoid importing `options` from connection packages.

Capabilities belong to a connection/security session and expire on closure; a replacement connection must probe again. An explicit safe CON GET probe (default `/.well-known/core`, application-overridable) establishes support only from a valid Q-aware response. A generic successful response that omitted Q support is insufficient.

`PreferKnown` selects classic when support is unknown. `Require` fails before payload transmission when support is unknown. An explicit probe is available to establish knowledge; ordinary writes never implicitly probe by sending their payload. Failed or ambiguous Q payload exchanges never trigger classic replay. A lost final response is an uncertain application outcome.

## Source map

- `net/blockwise/blockwise.go`: sequential assembly and token-scoped caches.
- `udp/client/conn.go`: `do`, `doInternal`, `handle`, `handleReq`, `processResponse`, `handleSpecialMessages`, `Process`, and `Close`.
- `message/option.go`: permissive option parsing drops invalid known option lengths.
- `message/options.go`: repeated-option support and unmarshalling.
- `udp/coder/coder.go`: UDP header and option decoding.
- `message/pool/message.go`: decoder retry on option capacity and pooled storage lifetime.
- `net/responsewriter/responseWriter.go`: single outgoing message lifecycle.
- `options/config/common.go`: coarse periodic expiry runner.
- `udp/server/server.go`, `dtls/server/server.go`: construction and configuration propagation.

The raw option preservation path is deliberately narrow. Extending critical-option enforcement for unrelated options is a separate compatibility change.

## Definition of release readiness

Both client/server directions pass deterministic reordering, loss, duplicate, timeout, cancellation, and shutdown tests. Combined Q-Block1/Q-Block2 works. UDP and DTLS exercise the same engine. Classic transfers remain covered. Independent interoperability is demonstrated with a pinned libcoap build, recording its version, build flags, commands, and traces. Unsupported methods/transports are documented and cannot accidentally enter the engine.
