# RFC 9177 Milestone 6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the release examples, support and limit documentation, and reproducible throughput and Q-owned-memory characterization for the accepted Milestone 5 subset.

**Architecture:** Add public UDP client and server examples that use the existing explicit capability probe, `PreferKnown`/`Require` modes, assembled handler delivery, response release, and caller contexts. Add a test-only loopback benchmark for small and multi-set Q-Block2 bodies with and without one dropped response block; read the existing manager and adapter accounting without adding public instrumentation. Publish the measured configurations and limits in the example guide and link that guide from the root README.

**Tech Stack:** Go 1.25+, go-coap UDP client/server, `net/qblock` accounting, Go benchmarks, loopback UDP.

**Spec:** `docs/superpowers/specs/2026-09-15-rfc9177-design.md`; Milestone 6 in `docs/superpowers/plans/2026-09-15-rfc9177.md`; accepted scope and capability contract in `docs/superpowers/plans/2026-10-01-rfc9177-milestone5-remaining.md` and `docs/superpowers/specs/2026-10-01-rfc9177-capability-selection-design.md`.

## Global Constraints

- Q data uses NON messages; explicit capability discovery uses a bounded CON GET.
- Outbound Q selection supports unicast UDP/DTLS GET and body-bearing POST/PUT after explicit discovery.
- `PreferKnown` uses existing behavior while capability is unknown or unsupported; `Require` fails before payload transmission unless capability is known supported.
- Q failures and lost final responses are not replayed through classic blockwise; application outcome may be uncertain.
- Capability knowledge belongs to one connection/security session and ends when that session closes.
- Observe, FETCH/PATCH/iPATCH, multicast, TCP/TLS, BERT and OSCORE remain deferred.
- Preserve the RFC 9177 limits, bounded transfer lifetime, and existing aggregate ownership accounting; do not claim process RSS from reservation counters.
- Keep all historical `.superpowers/sdd/` evidence and both user-owned modified documents unchanged.

## Review Focus

- An unknown peer must be probed explicitly before Require sends payload; pin this with example flow and a runnable loopback invocation.
- A canceled caller context must reach `Do`, and every successful pooled response must be released by the caller; pin this in the example and runtime invocation.
- A lost NON response block must recover with Q repair and no classic replay; pin the benchmark's dropped-block count and complete-body digest.
- Report client and server retained reservations separately and distinguish Q accounting from RSS; pin the exact configurations and benchmark metrics in the retained ledger.
- Documentation must not imply support for deferred methods/transports or universal speedup; reconcile the support table and report against Milestones 1–5 evidence.
