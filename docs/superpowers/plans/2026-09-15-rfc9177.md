# RFC 9177 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Use superpowers:subagent-driven-development only if parallel agent execution is selected. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver opt-in Q-Block transfers over UDP/DTLS with assembled application bodies, bounded recovery, and conservative fallback.

**Architecture:** Introduce a separate `net/qblock` engine and a connection adapter in `udp/client`. Preserve classic blockwise routing. Build and test wire/storage foundations before fixing the engine interface or enabling public configuration.

**Tech Stack:** Go 1.25.0, existing message/pool and UDP/DTLS packages, standard-library binary encoding, existing testify assertions, Go fuzzing and race detector.

**Spec:** [RFC 9177 implementation design](../specs/2026-09-15-rfc9177-design.md).

## Global Constraints

- NON Q-Block1 POST/PUT and Q-Block2 GET, client and server.
- Include Q-Block2 response bodies to POST/PUT, including combined upload/download exchanges.
- CON capability discovery must work before NON payload transmission is enabled.
- Keep `WithBlockwise` behavior unchanged.
- No new production dependency in the foundation milestone.
- Do not refactor classic `BlockWise` into a shared transfer engine.
- No incoming pooled message is retained past its callback by the Q engine.
- Failed or ambiguous Q payload exchanges never trigger classic replay.

## Plan status and granularity

This document contains the complete delivery roadmap and execution tasks for milestone 1. Milestones 2–6 have dependency, file, and acceptance boundaries; expand each into its own task-level plan when its predecessor is accepted. They are not authorization to improvise an entire state machine from a roadmap row. This keeps the first review small and avoids publishing speculative engine APIs.

Milestone 1 has been implemented in the isolated `feat/qblock-foundation` worktree. See [execution results](2026-09-15-rfc9177-results.md) for checks and limitations. Commit and integration steps remain pending; the full suite is not green on this host. Proposed names below become the contract for milestone 1; update this plan and affected tests together if review changes them.

### Milestone 2: transfer machines

Proposed files: `net/qblock/config.go`, `engine.go`, `transfer.go`, `qblock1.go`, `qblock2.go`, `timing.go`, `identity.go`, and matching tests. Add `net/qblock/engine_test.go` fixtures before implementing transitions.

Define these contracts in its detailed plan: owned packet snapshot, operation identity, transfer ID, event/action types, send-result reporting, next deadline, and terminal result. The engine does not depend on `udp/client`, pooled messages, or socket I/O.

Reviewable slices:

1. Identity and budgets: operation options plus Request-Tag collection; operation plus ETag; aggregate byte/transfer/token caps; bounded completed-operation records.
2. Q1 receiver: sparse intake, set acknowledgments, missing reports, single assembled delivery, retained outcome for late duplicates.
3. Q1 sender: initial ordered sets, repair prioritization, terminal response, no replay after uncertain completion.
4. Q2 sender: retained response, block selection, overlapping repair requests deduplicated, continuation recognition.
5. Q2 receiver: multiple responses per request token, representation change, missing requests, final assembly.
6. Timing: fixed set boundaries, stale Continue rejection, one jitter sample per body, receive backoff, retry limits, partial expiry, peer probing-rate budget, and MTU-bounded repair reports.

Acceptance scenarios: a 21-block body sends sets 0–9, 10–19, 20; a stale acknowledgment of 0–9 never advances the last set. Repairs for 8 and 12 respect the boundary. Lost first/middle/final data and lost recovery control packets terminate correctly. Every allocated byte/token is released after timeout. Handle SZX negotiation/rejection before offsets are committed. A Q1 terminal response may start a Q2 response body.

### Milestone 3: connection adapter

Proposed new files: `udp/client/qblock.go`, `qblock_scheduler.go`, and matching tests. Modify `udp/client/conn.go`, retaining small hooks at `do`, `handleReq`, `handleSpecialMessages`, and connection lifecycle points.

Reviewable slices:

1. Persistent ownership registry coordinated with classic/Observe token allocation; collisions retry or fail before writing. MID entries expire and cannot survive session replacement.
2. Route owned responses before one-shot handlers; route Resets before special-message dropping; route new Q requests before classic blockwise handling. Unowned traffic follows existing paths.
3. Send actions use explicit NON type, fresh MID, cloned options, and connection control information. Prevent `processResponse` from rewriting engine-produced messages to CON or sending a second response.
4. Capture handler output into bounded owned storage. Completed-upload records suppress application reinvocation. A response-cache hit for a CoAP MID and a duplicate body block with a new MID are distinct cases.
5. One scheduler per connection drives next deadline; serialize engine mutation; execute sends and callbacks outside locks. Start only when Q support is enabled and close once with connection lifetime.

Acceptance: one `Do` completes with a whole body despite many tokens/packets; ordinary `Do` and Observe coexist; terminal responses lacking Q options are delivered; Reset cancels its transfer; callbacks can call connection APIs without deadlock. Releasing/reusing every inbound message immediately must not corrupt retained bodies. Fail a send mid-burst and verify cleanup without fallback.

### Task 5: bounded missing-block CBOR sequences

**Files:** Create `net/qblock/missing.go`, `net/qblock/missing_test.go`.

**Interfaces:**

```go
func DecodeMissing(data []byte, blockCount uint32, maxItems int) ([]uint32, error)
func EncodeMissing(numbers []uint32, maxBytes int) (payload []byte, consumed int, err error)
```

Decoder `maxItems` limits wire items, including duplicates, before allocation. Output is increasing and deduplicated. An empty sequence, descending sequence, out-of-body number, invalid type, truncated integer, or limit violation returns an error. The future engine ignores malformed reports; this helper never decides transfer termination. Accept valid unsigned encodings even when wider than necessary.

Encoder requires a nonempty strictly increasing input and positive byte budget; return the largest whole-number prefix fitting the packet budget plus its consumed count. Error if even the first number cannot fit. This supports multiple bounded reports rather than one unbounded response.

### Task 6: sparse owned body assembly

**Files:** Create `net/qblock/body.go`, `net/qblock/body_test.go`.

**Interfaces:**

```go
type Metadata struct {
    Size uint32
    SZX blockwise.SZX
    ContentFormat message.MediaType
    HasContentFormat bool
    Identity []byte
}
type Body struct { /* private metadata, block map, count, and limits */ }
func NewBody(meta Metadata, maxBytes uint32) (*Body, error)
func (b *Body) Add(meta Metadata, block Block, payload []byte) (duplicate bool, err error)
func (b *Body) Missing(first, end uint32, limit int) []uint32
func (b *Body) Complete() bool
func (b *Body) Assemble() ([]byte, error)
```

`Identity` is an opaque copied key supplied by the future engine, not a hash or a replacement for semantic Request-Tag/ETag parsing. `Missing` uses a half-open block range, clips to the body's block count, and returns at most `limit` indices. A nonpositive limit or empty range returns no items. No concurrency guarantee: the future engine serializes access.
